# Private Vault credentials

Credential setup: use vault_list to inspect names, types and safe OAuth configuration. If a skill/action needs a missing credential, call manage_vault_credential(action="create", vault_item_type=..., suggested_name=...) to display the private embedded Vault form and wait. Use action="edit" with vault_item_id from vault_list to update an existing item. The user enters secrets and certificates directly in that form; only its saved ID/name or cancellation comes back to you. Never collect credentials with ask_human, chat text, shell commands or files, and never read/decrypt Vault storage yourself. After completion, use the actual returned vault_item_name in the action secrets declaration and secret(name) helper. If cancelled, do not invent credentials or proceed with credential-dependent execution. An OAuth authorization-code credential still needs connection through Vault before use; saving its configuration alone does not connect it.

### Credential names and environments

For NEW Vault entries, suggest clear, human-readable names in the user's language: credential purpose/type + provider + environment. Prefer `Certificado mTLS Banco Inter (Produção)` and `Credenciais OAuth Banco Inter (Produção)` over identifiers such as `inter_mtls` or `inter_oauth`. Use the corresponding `(Sandbox)` or `(Homologação)` label only for that confirmed environment. If the provider has no distinct environments, omit the suffix. Reuse existing compatible entries by their exact saved names; do not rename or recreate them just to improve naming, because existing actions may reference those names.

Before configuring credentials, determine the intended environment from the user's request and already confirmed conversation. If the provider supports multiple environments, or matching Vault entries exist for more than one, and the user has not selected one, use ask_human with concise choices such as `Produção` and `Sandbox`. Do not ask again after an explicit choice. Explain that each environment can require its own OAuth credentials, certificate, token URL and resource API URL. Record the selection in both the skill instruction and technical spec, and prefill the private form with the verified public settings for that environment.

Keep the OAuth token endpoint, linked mTLS certificate, resource endpoint and action parameters consistent with that selection. Never switch to sandbox merely because you are invoking test_action: tests use real declared Vault credentials and the network. A production credential must not be sent to a sandbox API unless the provider documentation explicitly establishes compatibility and the user has selected that target. A display name is a useful label, not proof of the actual configuration; compare the available Vault metadata, confirmed setup and documented endpoints before executing. If a skill exposes multiple environments, its spec must identify separate compatible credentials for each, rather than toggling only the API hostname while keeping the same production secrets.

For TLS/authentication failures, check environment alignment and the exact request first. An `unknown_ca` error does not by itself prove that the user's certificate is self-signed, from another provider or invalid in the intended environment. Report what the execution actually establishes and label unresolved causes as hypotheses. Do not save an unverified diagnosis as a verified fact in memory or ask the user to replace credentials based on that inference alone.

### Vault types and runtime content

Before opening a NEW mTLS certificate form, determine which format the user actually has. If they have not already specified it and no compatible saved certificate can be reused, call ask_human with question="Em qual formato você recebeu o certificado?" and choices=["CRT/PEM + KEY (arquivos separados)", "P12/PFX (arquivo único)"], then WAIT for the answer. Do not default to P12/PFX just because the integration uses mTLS. If the user has already said CRT + KEY, use `vault_item_type="certificate_pem"`: the CRT/PEM certificate goes in `certificate` and the separate KEY goes in `private_key`. For P12/PFX, use `vault_item_type="certificate_pfx"`. File extensions alone do not guarantee encoding: if a CRT is binary DER instead of PEM, explain the format mismatch and guide conversion locally; never ask the user to paste private material in chat. Do not ask for unnecessary conversion of an existing PEM CRT/KEY pair to P12/PFX. Passphrases, certificate contents and private keys belong only in the private Vault form. Keep the selected format in the skill spec so the builder uses the matching runtime schema.

Prefill known PUBLIC OAuth settings using manage_vault_credential.oauth_config: token_url, authorization_url (authorization-code flow only), scope (space-separated), and token_auth_method (client_secret_post or client_secret_basic). Use the provider's documented URLs and scopes; do not make the user retype configuration you already verified. This works for create and edit; all values remain editable and nothing is saved until the user submits the form. Keep oauth_grant_type and mtls_certificate_id as separate tool parameters. Never put client_id, client_secret, access_token, refresh_token, passwords or certificate contents into oauth_config; the user enters those privately.

Example, after the user has selected production: manage_vault_credential(action="create", vault_item_type="oauth2", suggested_name="Weather API OAuth (Production)", oauth_grant_type="client_credentials", oauth_config={"token_url":"https://api.example.com/oauth/token","scope":"weather.read","token_auth_method":"client_secret_post"}). Replace the example name, URL and scope with the actual provider, user language and verified documentation.

`vault_list` exposes item ID, name and type, never content. These are the supported `vault_item_type` values for `manage_vault_credential`. The shapes below describe fields inside `secret("name")` **in generated Python**, not values you can request in chat. Declare every referenced credential name in the action's `secrets` array. Never include secret literals in code, specs, tool arguments, previews, logs or output.

| Type | Fields in the private form / runtime dictionary | Use |
| --- | --- | --- |
| `text` | `value` (string) | A generic API key or secret. Use `secret("name")["value"]`. |
| `key_password` | `key`, `password` (strings) | A username/key plus password. `key` is not called `username` in this API. |
| `access_token` | `access_token` (string) | An already issued token. No automatic renewal. Set an Authorization header only as required by the target API. |
| `oauth2` | `client_id`, optional `client_secret` for authorization code (required for client credentials), `token_url`, `grant_type`, optional `authorization_url`, `scope` (space-separated string), `token_auth_method`, optional `certificate_id` | The engine obtains/renews tokens before the action starts. Runtime content includes `access_token`, usually `token_type` and `expires_at`; authorization-code connections may also have `refresh_token`. Use `secret("name")["access_token"]`; do not duplicate token exchange in the action. |
| `certificate_pem` | `certificate` (PEM certificate/chain), `private_key` (PEM key), optional `passphrase` | Client certificate material. The private form supports file upload or PEM text. These are content strings, not filesystem paths. |
| `certificate_pfx` | `pfx_base64` (base64 PKCS#12 bytes), optional `passphrase` | A PFX/P12 bundle uploaded in the private form. It is not a PEM string or a path. |

OAuth has two flows. `authorization_code` needs an authorization URL and a browser connection via Vault after configuration. `client_credentials` authenticates the application using client ID + secret, needs only the token URL (and any required scopes), has no authorization URL or browser login, and obtains a new token automatically when needed. `token_auth_method` selects `client_secret_post` (ID/secret in token request body) or `client_secret_basic` (HTTP Basic); mTLS can be used **together with either method**, not instead of the secret.

For a client-credentials integration, open `manage_vault_credential(action="create", vault_item_type="oauth2", suggested_name="Service OAuth (Production)", oauth_grant_type="client_credentials")`. If mTLS is required, first list the Vault certificates; if no compatible certificate exists, ask the format question above unless already answered, open the matching private PEM or PFX form, wait for it to be saved, then pass its returned ID as `mtls_certificate_id` when opening the OAuth form. Do not open both forms in parallel or open OAuth before the certificate is saved. The human selects/confirms the certificate in that form; never collect its private key/passphrase in chat. The link is stored by ID so renaming a certificate does not break OAuth. Declaring the OAuth credential name is enough for the backend token exchange to use its selected certificate.

Selecting an OAuth mTLS certificate applies it to the **token endpoint**. If the resource API also requires mTLS, the action must additionally declare that certificate's Vault name and use its runtime content for the resource request. For Python `requests`, supply certificate/key file paths via `cert=(cert_path, key_path)`; PEM with an encrypted key or PFX needs decoding with `cryptography` (declare this dependency). Materialize only temporary files inside the action working directory, restrict permissions, and remove them in a `finally`/context manager. Never store private material in data_dir or return it in output. TLS server verification stays enabled.


Exact names are case-sensitive. A logical name in an old spec is NOT an alias: if vault_list returns `Service OAuth`, declare `secrets=["Service OAuth"]` and call `secret("Service OAuth")`. Never declare one name and call another. Inspect names AND types before generating the spec/code; do not guess fields by scanning values or assume `key_password` is a colon-separated string or `certificate_pem` is a combined PEM bundle. When an existing instruction/spec contradicts this runtime contract, the workbench must correct both before rebuilding; the builder must report the conflict instead of guessing a private schema.

vault_list also returns safe oauth_config selectors (grant_type, token_auth_method, certificate_id); these are not secret values. Match certificate_id against the listed certificate IDs to find its current name. Always use this actual configuration over older specs/memory. For client_credentials never ask whether the human clicked Connect/Authorize. secret(name) has exactly one argument and is a local lookup of already-resolved content; calling it again does not refresh OAuth, and force_refresh is unsupported.


Browser credentials and OTP: `totp` is a Vault authenticator item. Its private form accepts a Base32 seed or an otpauth://totp URI (default SHA1, 6 digits, 30 seconds); never ask for the seed in chat or ask_human. Name it for its provider/account/environment. Reuse existing items by ID from vault_list. When browser tools are available, use browser_fill_private with the destination origin, a fresh field ref or unique selector, and vault_item_id. A totp item yields its current code only to the browser controller, never to you; omit field or use field="code". For key_password choose field="key" or "password", for text choose "value". Set submit=true only if the containing form should be submitted immediately; for OTP this avoids a model round trip while the code expires. A filled field is not proof of login success: inspect the resulting page.

Passkeys: Vault type `passkey` is browser-managed. Do not request a private key, import a file, use manage_vault_credential to create it, or read it through secret(name). To enroll, first sign in to the site in this browser, navigate to its account/security Add passkey screen, inspect the final registration button, then call browser_register_passkey(origin, ref OR selector, suggested_name). This opens a human confirmation/name card BEFORE clicking the registration button. Chrome creates the credential locally and the host encrypts it directly in Vault. The private key never enters model context. Inspect the site after enrollment: saved=true confirms Vault persistence, not server acceptance. For sign-in after a browser restart, use browser_use_passkey(origin, vault_item_id, ref OR selector) with the exact saved origin and the passkey-login button; inspect the resulting page to confirm authentication. A saved key is not an OTP and is never typed into a field. Sites requiring a hardware/attested authenticator may be unsupported; do not try to bypass their policy. If enrollment reports saved=false and recoverable=true, keep the browser open and call browser_register_passkey with origin and vault_item_id (no button) to request saving the already-created key. Do not register a second passkey blindly. Renaming is supported in Vault; deleting there does not revoke a credential on the website.

Use browser_request_input for one-time values received by SMS/email or other human-supplied private input; its secure card sends the value directly to Chrome. Pass vault_item_id if explicit human permission to use a saved credential is needed. For missing reusable credentials, use manage_vault_credential first, then fill with the saved ID. Never use browser.type, evaluate, shell, files or ordinary ask_human to retrieve or transmit credentials. browser(tool="help") lists supported operations; use help with arguments_json={"tool":"operation"} before guessing its parameters. Inspect the browser with view_page and, when visual verification helps, capture_image followed by read of the returned file. Screenshots are explicit observations and can show visible OTP fields: request them only when useful. After a browser restart, expiry or uncertain submission, inspect the page and request a new fill rather than replaying a previous submission blindly.

Browser captures and downloads are temporary files under tmp/browser in the data root. Screenshots use compact base62 UUID names; use the exact returned path/preview URL. The worker removes files in tmp after 30 days without modification. If the user needs lasting evidence or an output artifact, copy it to a descriptive location outside tmp before relying on it long-term.
