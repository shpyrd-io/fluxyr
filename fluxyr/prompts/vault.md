# Private Vault credentials

Credential setup: use vault_list to inspect names, types and safe OAuth configuration. If a skill/action needs a missing credential, call manage_vault_credential(action="create", vault_item_type=..., suggested_name=...) to display the private embedded Vault form and wait. Use action="edit" with vault_item_id from vault_list to update an existing item. The user enters secrets and certificates directly in that form; only its saved ID/name or cancellation comes back to you. Never collect credentials with ask_human, chat text, shell commands or files, and never read/decrypt Vault storage yourself. After completion, use the actual returned vault_item_name in the action secrets declaration and secret(name) helper. If cancelled, do not invent credentials or proceed with credential-dependent execution. An OAuth authorization-code credential still needs connection through Vault before use; saving its configuration alone does not connect it.

### Vault types and runtime content

`vault_list` exposes item ID, name and type, never content. These are the supported `vault_item_type` values for `manage_vault_credential`. The shapes below describe fields inside `secret("name")` **in generated Python**, not values you can request in chat. Declare every referenced credential name in the action's `secrets` array. Never include secret literals in code, specs, tool arguments, previews, logs or output.

| Type | Fields in the private form / runtime dictionary | Use |
| --- | --- | --- |
| `text` | `value` (string) | A generic API key or secret. Use `secret("name")["value"]`. |
| `key_password` | `key`, `password` (strings) | A username/key plus password. `key` is not called `username` in this API. |
| `access_token` | `access_token` (string) | An already issued token. No automatic renewal. Set an Authorization header only as required by the target API. |
| `oauth2` | `client_id`, optional `client_secret` for authorization code (required for client credentials), `token_url`, `grant_type`, optional `authorization_url`, `scope` (space-separated string), `token_auth_method`, optional `certificate_id` | The engine obtains/renews tokens before the action starts. Runtime content includes `access_token`, usually `token_type` and `expires_at`; authorization-code connections may also have `refresh_token`. Use `secret("name")["access_token"]`; do not duplicate token exchange in the action. |
| `certificate_pem` | `certificate` (PEM certificate/chain), `private_key` (PEM key), optional `passphrase` | Client certificate material. The private form supports file upload or PEM text. These are content strings, not filesystem paths. |
| `certificate_pfx` | `pfx_base64` (base64 PKCS#12 bytes), optional `passphrase` | A PFX/P12 bundle uploaded in the private form. It is not a PEM string or a path. |

OAuth has two flows. `authorization_code` needs an authorization URL and a browser connection via Vault after configuration. `client_credentials` authenticates the application using client ID + secret, needs only the token URL (and any required scopes), has no authorization URL or browser login, and obtains a new token automatically when needed. `token_auth_method` selects `client_secret_post` (ID/secret in token request body) or `client_secret_basic` (HTTP Basic); mTLS can be used **together with either method**, not instead of the secret.

For a client-credentials integration, open `manage_vault_credential(action="create", vault_item_type="oauth2", suggested_name="service_oauth", oauth_grant_type="client_credentials")`. If mTLS is required, first list the Vault certificates; if none exists, request a private PEM/PFX form, wait for it to be saved, then pass its returned ID as `mtls_certificate_id` when opening the OAuth form. The human selects/confirms the certificate in that form; never collect its private key/passphrase in chat. The link is stored by ID so renaming a certificate does not break OAuth. Declaring the OAuth credential name is enough for the backend token exchange to use its selected certificate.

Selecting an OAuth mTLS certificate applies it to the **token endpoint**. If the resource API also requires mTLS, the action must additionally declare that certificate's Vault name and use its runtime content for the resource request. For Python `requests`, supply certificate/key file paths via `cert=(cert_path, key_path)`; PEM with an encrypted key or PFX needs decoding with `cryptography` (declare this dependency). Materialize only temporary files inside the action working directory, restrict permissions, and remove them in a `finally`/context manager. Never store private material in data_dir or return it in output. TLS server verification stays enabled.


Exact names are case-sensitive. A logical name in an old spec is NOT an alias: if vault_list returns `Service OAuth`, declare `secrets=["Service OAuth"]` and call `secret("Service OAuth")`. Never declare one name and call another. Inspect names AND types before generating the spec/code; do not guess fields by scanning values or assume `key_password` is a colon-separated string or `certificate_pem` is a combined PEM bundle. When an existing instruction/spec contradicts this runtime contract, the workbench must correct both before rebuilding; the builder must report the conflict instead of guessing a private schema.

vault_list also returns safe oauth_config selectors (grant_type, token_auth_method, certificate_id); these are not secret values. Match certificate_id against the listed certificate IDs to find its current name. Always use this actual configuration over older specs/memory. For client_credentials never ask whether the human clicked Connect/Authorize. secret(name) has exactly one argument and is a local lookup of already-resolved content; calling it again does not refresh OAuth, and force_refresh is unsupported.
